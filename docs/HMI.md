# HMI on Runtime v4

Operator screens designed in the OpenPLC Editor run **in the browser**. The device serves the
browser client and the PLC values its screens show, and applies the writes they make: a native
plugin, `build/hmi/libhmi_plugin.so`, loaded into `plc_main` beside any board (VPP) plugin, holds
no screen code. Browsers reach it through the runtime's own HTTPS server: the client at `/hmi/` and
the value channel on the Socket.IO namespace `/api/hmi`, port 8443, no extra port.

```
browser (screens, layout, input, drawing: hmi.wasm)
   │ HTTPS/WSS: open, show screen, write tag  ▲ values of the screen shown
   ▼                                          │
web server (webserver/hmi_proxy.py) ──Unix socket──> HMI plugin in plc_main
/hmi/ assets, /api/hmi, accounts        hmi.socket     host + manifest (hmi_access.c, data)
                                                        │ debug_read / debug_write (soft)
                                                        ▼
                                                      PLC program .so
```

Authentication, the account's role, sign-out, revocation and session expiry stay on the device
(web server). What a viewer may read and write is decided by the plugin from the manifest the
editor built, never from what the browser sends.

## Upload artefact

A runtime that accepts it says so with `"hmi": true` at `GET /api/capabilities` (unauthenticated).
A Runtime v4 upload may carry an `hmi/` folder next to the program sources:

| Path in the upload | Content |
| --- | --- |
| `hmi/manifest.json` | `{"format": 2}`; anything else is refused, `{"format": 1}` (an HMI built for screens run on the device) included, with a message naming the format |
| `hmi/src/` | The host-side manifest: `hmi_access.h` and the generated `hmi_access.c`. Only `.c` and `.h` files, directly in `hmi/src/` |
| `hmi/client/` | The browser client, `hmi.wasm` included. Only `.html`, `.js`, `.css`, `.wasm`, `.txt` and `.ttf` files (extensions in lower case), names matching `^[A-Za-z0-9._-]{1,64}$`, no subfolders |

- `.js`, `.wasm` and `.html` stay refused anywhere else in an upload.
- An upload with `hmi/` replaces the previous HMI. An upload without `hmi/` keeps it; its MD5 then no
  longer matches the program and it reports "out of date" (TC12).
- An `hmi/manifest.json` with `{"format": 2, "remove": true}` and nothing else removes the HMI.
- An editor and a runtime of the same release go together: there is no fallback to an older format.

## Manifest (`hmi_access.h`)

Data only, generated by the editor from the instance paths STruC++ resolved in each screen:

- `hmi_access_tags[]`: each PLC variable screens use, by tag id: debug address (`arr`, `elem`),
  type, `max_len` of a STRING, canonical path (for logs).
- `hmi_access_pages[]`: each screen, by page number: the tags it reads (ascending ids), how it writes
  tags (`hmi_access_write_t`, ascending tag: `whole` when screen code assigns the whole value, `bits`
  the mask of the bits it assigns one at a time with `Tag.n := ...`; an assignment is a write, a bit
  assignment a read and a write of that bit, anything else a read; code outside screens counts for
  every screen), the limit of each whole-written tag (below) and the roles that may open it, one bit
  per role (bit 0 admin, always set; 1 engineer; 2 operator; 3 viewer) from the HMI Settings role grid.
- Write limits (`limited`, `min`, `max`): what a screen can write to a tag as far as the build knows it
  statically, in the tag's own values (integers rounded outwards and clamped to the type, REAL as the
  float the widget computes; for a STRING, its length in bytes):
  - a two-way widget bound to the tag: its declared value range (`hmi_range` on the widget's NewValue:
    slider, knob, stepper and numeric input `MinValue..MaxValue`; selector `0..2`; option buttons and drop-down the
    index of the last option) or text length (`hmi_max_length`: text input `MaxLength`), from the
    element's literal properties or the widget's defaults;
  - an assignment of a literal: that value (a STRING literal, its length);
  - the union of all of them on that screen; **no limit** when any write on the screen has none: a
    widget without a declared range, a range input that screen code changes
    (`Slider.MaxValue := ...`) or that is not a literal, or an assignment of any other expression.
  - The numeric input's MinValue and MaxValue default to -1.0E38 and 1.0E38 (the convention of the
    gauge's zones for "off"): its tag is then limited only to that and the type's range. An entry
    outside an input's range is refused in the browser already: the keyboard's OK delivers nothing.
- `hmi_access_plc_md5`, the program the screens were built against, and `hmi_access_period_ms`, the
  screens' frame period from HMI Settings.

The plugin checks the manifest at `init` (types, sizes, sorted lists naming known tags); one it
cannot serve leaves the HMI out of date.

## Build and seal

`scripts/compile-hmi.sh` builds the plugin after the program when `core/generated/hmi/` exists:

- sources: the runtime's host (`core/src/drivers/plugins/native/hmi/*.c`) plus `hmi/src/*.c`;
- flags: `-std=c11 -Wall -Wextra`, position independent;
- output: `build/hmi/libhmi_plugin.so`; `hmi/client/*` is copied to `build/hmi/client/`. The build
  goes to `build/hmi.new` and replaces `build/hmi` only when it succeeds;
- a failed build (program or HMI) changes nothing on the device: the PLC is not stopped, the running
  program's `.so` is not replaced and the installed HMI stays;
- seal: `build/hmi/hmi.seal`, one line per file, `<sha256 hex>  <path relative to build/hmi>`, covering
  the plugin and every client file. `plc_main` checks the plugin's line before `dlopen` and loads only
  `libhmi_plugin.so` from `build/hmi`; the web server checks a client file's line before serving it. A
  missing or mismatching seal refuses the file.

The plugin is registered by `plc_main` itself (not through `plugins.conf` or `vpp_plugins.conf`)
whenever `build/hmi/libhmi_plugin.so` exists, under the name `hmi`.

## Plugin arguments

`plugin_runtime_args_t` gains `char program_md5[33]`: the running program's MD5 (the value the debugger
verifies), NUL-terminated, empty when no program is loaded. The Python ctypes mirror
(`core/src/drivers/plugins/python/shared/plugin_runtime_args.py`) follows.

The host compares it with `hmi_access_plc_md5`. On a mismatch, or when either is empty, the HMI is
**out of date**: it opens no viewer, makes no debug read or write, and answers every OPEN with
STATUS out_of_date.

Values cross in **wire format**: a number in its IEC width, little endian (BOOL one byte, 0 or 1;
TIME, LTIME, TOD and DT signed nanoseconds and DATE days since 1970, 8 bytes each); a STRING as its
text without a NUL. The host converts between it and the STruC++ debug format of `debug_read` /
`debug_write` (soft write, respects forcing).

## Host

- Socket: `/run/runtime/hmi/hmi.socket`, in a directory `start_loop` creates (or takes over when it is
  a real directory of the same user, not a symlink) with mode 0700; the socket is removed in
  `stop_loop`. One connection at a time, from the web server, which connects only when the directory
  is owner-only and both belong to its own user.
- Viewers: OPEN carries the role and account the web server verified; OPENED answers at once. BUSY
  answers an allocation failure, an account name that is not printable UTF-8 (that viewer only; the
  connection stays) and a request queue overflow; there is no viewer limit.
- Requests: a viewer's SHOW and WRITE requests are queued in arrival order (at most 128 requests and
  64 KiB per viewer; more closes that viewer with BUSY) and applied in that order by the value thread,
  so a write is always checked against the screen shown when it was made.
- SHOW of page `p`: served when `p` is a screen of the manifest and the viewer's role bit is set; its
  read list is then the only set of tags the viewer is sent, starting with all of them. Otherwise
  REFUSED (show, `p`), a log line with the account and role, and the viewer is served no tag until a
  granted SHOW.
- BIT of tag `t`, bit `n`: applied only when a screen is shown and its write entry for `t` has bit `n`
  set; the host reads the variable's current value, changes that one bit and soft-writes it, so bits
  the PLC changed since the browser last saw the value stay (logged as `PATH.n = TRUE (now <value>)`).
  The read and the write are two debugger calls, not one atomic step against the scan. Anything
  else is REFUSED (write, `t`).
- WRITE of tag `t`: applied (debug soft write, logged with the account, path and value) only when a
  screen is shown, its write entry for `t` is `whole` (a tag the screen only sets bits of takes no
  whole value), the value fits the tag and, when the entry is `limited`, lies within `min..max` (exact width; BOOL 0 or 1;
  REAL and LREAL finite; TOD within a day; STRING at most `max_len` bytes and no NUL). Anything else
  is REFUSED (write, `t`), logged with the reason, and never reaches the PLC. Every write, applied or
  refused, counts in the viewer's write count, and a tag the screen reads is sent again after it.
- Values: every `hmi_access_period_ms` (10-10000 ms) the value thread reads the tags of each viewer's
  screen and offers the values that changed since that viewer was last sent them. A viewer has at
  most one VALUES message waiting; changes made before the writer took it are merged into it, so a
  slow web server or viewer never delays another viewer or the PLC, and no change is lost. A message
  is also sent after a SHOW and after writes, so the write count reaches the browser.
- Logs: the number of viewers on every open and close, writes, refusals.
- Threads run at the default priority (`SCHED_OTHER`, nice 0); PLC tasks keep `SCHED_FIFO`.
- Stop: `stop_loop` joins both threads; no screen code runs in `plc_main`, so nothing can hold it.

## Wire protocol (web server <-> host)

Every message: `u32 length (LE) | u8 type | payload`, `length` counting type and payload, at most
4 MiB (from the web server: at most 1037 bytes). Integers little endian. A malformed message closes
the connection.

Web server to host:

| Type | Name | Payload |
| --- | --- | --- |
| 0x01 | OPEN | `u32 viewer, u8 role (0 admin, 1 engineer, 2 operator, 3 viewer), u8 name length, name (UTF-8, at most 64 bytes; the web server replaces control characters with '?')` |
| 0x02 | CLOSE | `u32 viewer` |
| 0x03 | SHOW | `u32 viewer, u16 page` |
| 0x04 | WRITE | `u32 viewer, u16 tag, u16 length, value (at most 1024 bytes, wire format)` |
| 0x05 | BIT | `u32 viewer, u16 tag, u8 bit (0-63), u8 value (0 or 1)` |

Host to web server:

| Type | Name | Payload |
| --- | --- | --- |
| 0x81 | STATUS | `u8 state (0 live, 1 out_of_date)` |
| 0x82 | OPENED | `u32 viewer` |
| 0x83 | BUSY | `u32 viewer` |
| 0x84 | VALUES | `u32 viewer, u16 page (0xFFFF: none served), u32 writes (the viewer's writes processed), u16 count`, then `count` records `u16 tag, u16 length, value` |
| 0x85 | REFUSED | `u32 viewer, u8 what (0 show, 1 write), u16 page or tag` |

## Web server (`webserver/hmi_proxy.py`)

- `GET /hmi/` and `/hmi/<file>` serve `build/hmi/client/`, names whitelisted, each file checked against
  the seal, with `Content-Security-Policy: default-src 'self'; script-src 'self' 'wasm-unsafe-eval';
  connect-src 'self'; img-src 'self' data:; style-src 'self'; frame-ancestors 'none'; base-uri 'none';
  form-action 'self'`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store` and
  `Referrer-Policy: no-referrer`. Only the sign-in page and its static files are public:
  `index.html`, `hmi.css`, `hmi-client.js`, `socket.io.min.js`, `socket.io-LICENSE.txt` and
  `fonts-LICENSE.txt` (`PUBLIC_ASSETS`); none of them carries anything of the project. Every other
  client file, `hmi.wasm` (all the project's screens) above all, needs `Authorization: Bearer` with an
  access token that passes the same checks as the `/api/hmi` connect (signature, expiry, revocation,
  session, account, a role that may open the HMI). Without one a script's request gets 401 and a page
  load (`Sec-Fetch-Mode: navigate`, or `Accept: text/html` without that header) is redirected to
  `/hmi/`; each refusal is logged. Served files keep `Cache-Control: no-store`, so no cache holds the
  module after sign-out. Every signed-in role receives the same module, with every screen; what each
  role may read and write is enforced by the host (see Host). `hmi.wasm` is served with
  `X-HMI-Build`, the sha256 of the bytes served (the module's seal line).
- HMI build ID: the sha256 the seal records for `client/hmi.wasm`, read when the web server connects
  to the host, so it names the build the running plugin was loaded with (`plc_main` loads the plugin
  only after checking the same seal). An upload replaces `build/hmi` before the PLC stops; until the
  host comes back with the new plugin, the build ID stays the old one, and `hmi.wasm` on disk (and its
  `X-HMI-Build`) is already the new one.
- Namespace `/api/hmi`: the access token is checked at connect (`auth.token`) with the same rules as
  every endpoint (signature, expiry, revocation, session, account, role in `webserver/access.py`).
  While connected it is re-checked every 5 seconds and on each client event for revocation, session,
  account and role, as the debugger does; expiry is enforced at connect only, so a renewal does not
  interrupt a viewer. A refused token or a role change disconnects. The role sent in OPEN is the
  account's, from the database.
- Client event `in`, rebuilt from whitelisted, range-checked fields (booleans refused as numbers):
  `{t:"o",n}` open (a second one closes the viewer on the host and opens it again, its write count
  from 0), `{t:"s",p,n}` show screen `p` (0-65534), `{t:"b",g,b,v,n}` set bit `b` (0-63) of tag `g` to
  `v` (0 or 1), `{t:"w",g,v,n}` write tag `g` (0-65534) with `v`
  the value's bytes (a Socket.IO binary, at most 1024 bytes). A show or write that does not check out
  is forwarded as one naming 0xFFFF, which the host refuses, so the write count stays the browser's.
  `n` is the client's sequence number (0 to 2^53); events are forwarded in `n` order per viewer, at
  most 64 held; an invalid event still uses its number. Shows, writes and bit writes carry `h`, the
  HMI build ID the client's module was loaded with (64 lower-case hex digits), and are forwarded
  only when it is the build of the host connection the viewer was opened on; one without `h` or
  with another build is dropped and logged (it still uses its number). Shows and writes before the
  viewer is open on the host, or while the host is down, are dropped.
- Server events: `hmi_values` (the VALUES payload after the viewer id) is sent with an
  acknowledgement: until the browser acknowledges it, newer values for that viewer are merged (newer
  values win; values for another screen replace them) and sent together once it does (after 1 second
  without an acknowledgement they are sent anyway). `hmi_refused` `{what: "show"|"write", id}`.
  `hmi_status` carries `state`: `live` with `role` and `build`, the HMI build ID (sent on OPENED; the
  browser runs the screens of that build with that role), `stopped` (the HMI is installed but the PLC is stopped: viewers stay connected and are
  opened again on start), `out_of_date` (to every viewer, and to viewers that connect later), `busy`
  (the host refused this viewer, see Host; its next open retries) or `unavailable` (no HMI installed).
  A message the web server cannot handle drops the host connection, which is then opened again; it
  never stops the HMI for good.

## Browser client (`hmi/client/`)

The editor ships the client with every HMI; the runtime serves it as it is. It is a page with no inline
script or style (the CSP above), `hmi-client.js`, socket.io-client 4.8.1 and `hmi.wasm`: the project's
screens (the generated unit), the HMI core and the unit's font table with a browser host, so a browser
draws the same pixels as the editor's preview and a panel. Licence texts ship beside it
(`fonts-LICENSE.txt`, `socket.io-LICENSE.txt`).

- Screens module: fetched once signed in, with `Authorization: Bearer` and the token, and compiled
  from the bytes; a refused fetch (401 or 403) returns to the form. Signing out drops the module, so
  the next account fetches it again with its own token. The module is kept with its `X-HMI-Build`.
  A `live` whose `build` differs from the running module's stops the screens (the old module's
  queued writes are dropped) and loads that build: the module is fetched again, and while the one
  served is not that build (the new HMI is installed but its plugin not yet loaded) the screens stay
  stopped with "HMI updating, please wait" until the next `live`. Every show and write carries the
  running module's build.
- Sign in: the page's form posts to `/api/login`; a 401 shows "Wrong user name or password.", a 429
  the wait from `Retry-After`. The token is kept in the browser's `localStorage`, so a reload or a
  browser restart on the same device stays signed in while the token is valid.
- Renewal: `/api/renew` three minutes before the 15-minute expiry, retried every 30 seconds while the
  device cannot be reached. Tabs of one browser share the stored token, and a renewed token is refused
  (presented again after 10 seconds it ends the whole session), so tabs renew one at a time (a Web
  Lock) and a tab whose token another tab renewed takes the stored successor of the same session
  instead of presenting its own: before renewing, when a renewal or a request is refused, and on the
  browser's storage event. The form clears the stored token only when it belongs to the same session. A token that expires first, a refused renewal or a disconnect whose
  `/api/whoami` answers 401 return to the form.
- Screens: on `live` the client starts the screens with the role the device sent, runs a frame every
  frame period (layout, input, keyboard, popups and animation all local), sends a show for the page
  shown and draws only the bands that changed. A newly shown screen is drawn once its first values
  arrive (or after 1 second). A screen's write changes the local value at once and is sent as a
  write, a bit assignment as a bit write; values the device sent before it processed that write are
  skipped for that tag. Every write is tagged with the screen shown when screen code made it, and the
  client sends a screen's show right before its first write: the old screen's writes (its OnHide)
  go before the new screen's show, the new screen's (its OnShow and first frame) after it.
- Notices: `stopped` "PLC stopped", `out_of_date` "HMI out of date, rebuild the project", "HMI
  updating, please wait" (see Screens module), `busy` "Device
  busy, try later" (asked again after 5 seconds), `unavailable` "No HMI installed", "Device
  unreachable, reconnecting" while the socket is down, and a screen fault (an IEC fault in screen
  code stops the module) "The screen stopped on an error; restarting": the screens start again
  after 5 seconds.
- Sign out: only through the project's screens. A screen's button calls `HMI_SignOut()` (the designer's
  "Sign out" action); the client ends the session with `/api/logout` and returns to the form. The
  client draws nothing over the screens; a session also ends when its token expires unrenewed, is
  revoked, or the account changes.
- `HMI_Lock()` and `HMI_Calibrate()` do nothing here. The PIN entry, the startup screen and the touch
  calibration belong to a board's own panel; a browser viewer signs in with its account and points
  with a calibrated device.
- While a notice shows, the screens stop, the last frame stays visible, dimmed and grey, and takes no
  input.

## Known limits

- **Screen-code conditions are not enforced on the device.** Screens run in the browser, which the
  client controls. The host enforces the role's screens, each screen's read and write lists, the bits
  it sets, the types and the static limits above. It cannot enforce what screen code decides at run
  time: an interlock (`IF Ready THEN Main.Start := TRUE; END_IF`), a value computed from others, a
  limit the code changes. A crafted client can write any value inside a tag's limit (any value of
  the type when the screen leaves the tag unlimited) at any moment the screen is shown. The PLC
  program must validate every variable an HMI screen writes, and must not rely on screen code for
  safety interlocks.

- STRING tags are read and written through the debug interface, which carries a string in a
  126-character window: a STRING declared longer than 126 is truncated when read and cut when written
  (the cut is logged). Accepted for this release (developer decision 2026-11-16).
